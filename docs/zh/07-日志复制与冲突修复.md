# 07. 日志复制与冲突修复

> **导航：** [← 06. BitCask 与日志键空间](./06-BitCask与日志键空间.md) · [08. 线性一致读 →](./08-线性一致读.md) · [索引](./README.md)

04 写了「成功路径上的 Append」。本文写 **不匹配、拒绝、探测、截断冲突尾**。源码：`Leader::maybe_send_append`、`Follower` 的 `Append` 分支、`Log::splice`（`src/raft/node.rs`、`log.rs`）。

---

## 1. 每个 Follower 的进度

Leader 为每个 peer 维护 `Progress`：

| 字段 | 含义 |
|------|------|
| `match_index` | 已确认与 Leader 一致的最高索引（初值 0） |
| `next_index` | 下一条要发给该 peer 的索引（初值 `last_index+1`） |
| `read_seq` | 该 peer 确认过的读序号 |

不变量（实现中 assert）：

```text
match_index <= last_index
match_index < next_index <= last_index + 1
```

---

## 2. 稳态：直接追加

客户端写 → Leader `append` 得到 `index = L`：

```text
若 peer.next_index == L:
  发送 Append {
    base_index: L-1,
    base_term:  Entry(L-1).term  (L==1 时 base=0,0),
    entries:    [Entry(L), ...]  // 最多 max_append_entries
  }
  乐观推进 next_index 到 batch 末尾 + 1
```

Follower：

```text
if base_index==0 || log.has(base_index, base_term):
  splice(entries)
  AppendResponse { match_index: last_of_batch, reject_index: 0 }
else:
  AppendResponse { match_index: 0, reject_index: min(base, last+1) }
```

Leader 收成功响应：`match_index = max(...)`，`next_index = max(next, match+1)`，再 `maybe_commit_and_apply`，并可能继续发后续 batch。

---

## 3. 为何会冲突？

典型场景：

1. 旧 Leader 已 append 但**未提交**的条目  
2. 网络分区后新 Leader 在相同 index 写入**不同 term** 的条目  
3. Follower 日志更短 / 分叉  

论文保证：以 **新 Leader 的日志为准** 覆盖冲突的未提交尾部（已提交的不会被覆盖）。

---

## 4. 拒绝与回退（reject）

Leader 收到：

```text
AppendResponse { match_index: 0, reject_index: R }  // R > 0
```

处理：

```text
若 R <= 当前 match_index → 过时响应，忽略
否则 regress_next(R)：
  next_index = max(R, match_index+1) 且 < 旧 next
  再 maybe_send_append(peer, probe=true)
```

---

## 5. 探测（probe）：空 Append

`probe=true` 时：

```text
Append {
  base_index: next_index - 1,
  base_term:  ...,
  entries:    []      // 空
}
```

含义：只问「你的 base 是否匹配？」，不送数据。

- 匹配 → `match_index = base`，之后改发真实 entries  
- 不匹配 → 继续减小 `next_index` 再探  

也可由 **HeartbeatResponse.match_index==0** 触发：把 `next_index` 调到 `last_index` 附近开始探。

```text
next_index 从高到低探测
    │
    ▼
找到公共 base ──► 连续 Append 追平 ──► match_index == leader.last
```

---

## 6. Follower 上的 splice（截断冲突尾）

`Log::splice(entries)` 要点：

1. 与本地重叠且 **term 相同** 的前缀跳过  
2. 从 **第一个 term 冲突** 的 index 起：  
   - 删除本地 `index..old_last` 的 Entry 键  
   - 写入新 entries  
3. **禁止**写到 `commit_index` 及以下（已提交不可改）  
4. 成功后更新 `last_index/last_term`  

因此「冲突修复」= **在 Follower 上用 Leader 的未提交后缀替换本地未提交后缀**。

---

## 7. 与提交的关系

- 只有 `match_index` 形成 **当前配置的 quorum**，且条目 **term == 当前领导 term** 才能抬 `commit_index`  
- 旧任期条目不能仅因复制到多数就提交（论文 5.4.2）；靠当选时的 **noop** 间接提交  

---

## 8. 落后超过本地日志：快照

若 `next_index < log.first_index()`（本地已 compact）：

```text
发送 InstallSnapshot { last_included_*, data, membership }
```

见 [11. 快照与落后追赶](./11-快照与落后追赶.md)。

---

## 9. 时序：分叉修复简图

```text
Leader log:  ... 10@T5, 11@T6, 12@T6
Follower:    ... 10@T5, 11@T5(未提交旧主)

Append base=11 term=6 entries=[12...]  → 拒绝（11 的 term 不是 6）
probe base=10 ...
匹配 10 → Append entries=[11@T6, 12@T6]
Follower splice：删掉旧 11@T5，写入新 11、12
```

---

## 10. 源码锚点

| 行为 | 位置 |
|------|------|
| 发送 append/probe | `maybe_send_append` |
| 拒绝回退 | Leader `AppendResponse` reject 分支 |
| 接受推进 | `Progress::advance` |
| 本地安装 | Follower `Append` + `Log::splice` |
