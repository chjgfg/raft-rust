# 01. 架构总览

> **导航：** [文档索引](./README.md) · [02. 消息与数据结构 →](./02-消息与数据结构.md) · [索引](./README.md)

本文描述 raft-rust 的进程形态、软件分层，以及「客户端 → 任意节点 → 领导者 → 存储」的总路径。更细的选举与存取见 03、04。

---

## 1. 一句话定位

**可多进程部署的教学向 Raft + 字符串 KV。**

- 协议核心：`Node::step` / `Node::tick`（`src/raft/node.rs`）
- 持久化：`Log` 把 term/vote/条目写进 `storage::Engine`（默认 **BitCask**）
- 应用状态：`SessionState` 包装 `Kv`（内存 `BTreeMap`，可 snapshot）
- 部署：每个 OS 进程一个节点（`raft-node`），节点间 TCP；客户端 `raft-cli`

没有生产级 TLS、没有分块快照流、没有完整运维面。

## 2. 进程与角色

### 2.1 部署进程

```text
┌─────────────┐     TCP WireMsg      ┌─────────────┐
│ raft-node 1 │◄───────────────────►│ raft-node 2 │
│ :7001       │                      │ :7002       │
│ data/node1  │                      │ data/node2  │
└──────▲──────┘                      └──────▲──────┘
       │ Client / ClientReply                │
       └──────────── raft-cli ───────────────┘
                         │
                    (也可连 node3)
```

| 进程 | 职责 |
|------|------|
| `raft-node` | 加载 YAML、开 BitCask、监听 TCP、驱动 `tick`/`step`、转发 peer 消息 |
| `raft-cli` | 编码 put/get、维护本地 `.raft-cli-session`、对 peers 列表重试 |

单节点：`peers: []`，`Node::new` 时直接成为 **Leader**。

### 2.2 Raft 角色（逻辑）

同一物理进程内，角色是 `Node` 枚举的一种：

| 角色 | 何时出现 | 对外服务客户端？ |
|------|----------|------------------|
| **Follower** | 默认；有领导时跟随 | 只**转发** ClientRequest，不本地写日志 |
| **Candidate** | 选举超时；含 PreVote / Election 两相 | 对 ClientRequest 直接 **Abort** |
| **Leader** | 真选举获多数票 | **唯一**执行 Write 复制与线性一致 Read |

## 3. 软件分层

```text
┌──────────────────────────────────────────────────────────┐
│  入口                                                     │
│  · raft-cli          src/bin/raft_cli.rs                  │
│  · raft-node         src/bin/raft_node.rs                 │
│  · 测试进程内集群     src/cluster/                        │
└───────────────────────────┬──────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────┐
│  网络                                                     │
│  · 帧：u32 LE 长度 + bincode(WireMsg)   src/net/codec.rs │
│  · 监听 / PeerOutbox                    src/net/transport │
└───────────────────────────┬──────────────────────────────┘
                            │ Envelope / Client 注入
┌───────────────────────────▼──────────────────────────────┐
│  Raft 核心  src/raft/node.rs                              │
│  · Follower / Candidate / Leader                          │
│  · 选举、复制、提交、读确认、成员变更、快照                  │
└───────────────┬───────────────────────────┬──────────────┘
                │                           │
                ▼                           ▼
┌───────────────────────────┐ ┌────────────────────────────┐
│  Log  src/raft/log.rs     │ │  State                     │
│  Entry / TermVote /       │ │  SessionState → Kv         │
│  CommitIndex / Snapshot*  │ │  apply / read / snapshot   │
└─────────────┬─────────────┘ └────────────────────────────┘
              │
              ▼
┌───────────────────────────┐
│  storage::Engine          │
│  BitCask  data_dir/bitcask.log
└───────────────────────────┘
```

**关键解耦：**

- Raft 日志 ≠ 应用 KV 表。日志在 BitCask；`Kv.data` 在进程内存，靠 apply / snapshot 恢复。
- 客户端字节命令经 `Request` 进入；日志里存的是 `Entry.command`（可能再包一层 Session）。

## 4. 两种「日志」别混

| 名字 | 是什么 | 在哪 |
|------|--------|------|
| **Raft 日志** | 共识复制的命令序列 `Entry` | BitCask 键 `Key::Entry(index)` |
| **BitCask 文件日志** | 存储引擎的追加文件 | `data_dir/bitcask.log` 整文件 append |

`Log::append` 会调用 `engine.set(Entry键, bincode(Entry))`，于是 **一条 Raft 条目 = BitCask 上的一次 set（可能再 append 一段文件）**。

应用层 `put a=apple` 成功后：

1. Raft 日志多一条 Put 命令；  
2. **多数节点**的 `Kv.data` 里都有 `a→apple`；  
3. BitCask 里主要是 Raft 元数据与条目，**不是**直接以 `a` 为键存业务字符串（业务在状态机内存）。

## 5. 时间与驱动

| 概念 | 含义 |
|------|------|
| `TICK_INTERVAL` | 100ms，一个逻辑 tick |
| `tick()` | 推进选举超时 / 心跳 / CheckQuorum |
| `step(Envelope)` | 处理一条入站消息（角色可能切换） |

`raft-node` 主循环（简化）：

```text
select!
  tick        → node = node.tick()
  inbound     → Raft: step(env)  /  Client: 包成 ClientRequest 再 step
  node_rx 出站 → to==self 则回 CLI；否则 PeerOutbox.send_raft
```
