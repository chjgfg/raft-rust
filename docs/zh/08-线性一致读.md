# 08. 线性一致读（read_seq）

> **导航：** [← 07. 日志复制与冲突修复](./07-日志复制与冲突修复.md) · [09. Session 与 CLI 幂等 →](./09-Session与CLI幂等.md) · [索引](./README.md)

04 简述了读要走领导。本文说明 **为什么读不进日志**、**何时允许 `State::read`**、以及 **read_seq 多数确认** 如何工作。源码：`Leader` 的 `ClientRequest::Read`、`maybe_read`、`Heartbeat`/`Read` 消息。

---

## 1. 目标语义

**线性一致读**：读到的值，要像在单机上与写操作排在同一全序里——不能读到「已经没有领导资格的旧主」上的过期状态，也不能在本任期状态尚未追上时读。

本实现：

- 读 **不** 写 Raft 日志（不做「读也共识一轮」）  
- 只在 **Leader** 执行 `State::read`  
- 执行前要 **多数节点确认** 该领导仍在本任期执政（通过递增的 `read_seq`）

无领导者租约（lease）：每次读都可能触发一轮多数 RPC（可用 Heartbeat 捎带）。

---

## 2. 端到端步骤

```text
1. 客户端 Request::Read(bincode(Get/Scan))
2. 任意节点 → 转发到 Leader（同写）
3. Leader:
     role.read_seq += 1
     reads.push_back({ seq, from, id, command })
     broadcast Message::Read { seq: read_seq }
     // 单节点：直接 maybe_read
4. Follower（认当前领导）:
     回复 ReadResponse { seq }
     // 或 HeartbeatResponse 里带回心跳中的 read_seq
5. Leader progress[peer].read_seq 推进
6. maybe_read():
     门闩通过 且 多数已确认 >= 某 seq
     → 按序 state.read → ClientResponse::Read
```

---

## 3. 两个门闩（`maybe_read`）

在数多数之前：

```text
(commit_term, commit_index) = log.get_commit_index()
applied = state.get_applied_index()

若 commit_term < 当前 term:     还不读   // 本任期还没有任何提交
若 applied < commit_index:      还不读   // 状态机落后于已提交日志
```

### 为何需要「本任期已提交」？

新领导当选时会 `propose(None)` 追加 **noop**。只有 noop（或本任期其它条目）提交后，`commit_term == current term`，才保证：

- 领导日志已包含先前任期的已提交前缀  
- 本地 apply 至少追到安全点，避免读到「未包含旧提交」的陈旧状态机  

这与论文 / 常见实现中的 **ReadIndex / 领导任期提交** 动机一致。

---

## 4. 如何计算 quorum_read_seq

```text
matched_seq = [(self, role.read_seq)]
            + [(peer, progress[peer].read_seq) for peer]

在所有出现过的 seq 从大到小：
  令 S = { 节点 | 其确认的 read_seq >= seq }
  若 membership.has_quorum(S):
    quorum_read_seq = seq; break
```

然后：

```text
while reads 队首.seq <= quorum_read_seq:
  pop → state.read(command) → 返回 ClientResponse
```

读队列按 seq 有序；小的先完成。

---

## 5. Heartbeat 与 Read 消息的关系

| 消息 | 作用 |
|------|------|
| `Message::Read { seq }` | 专门为读确认广播（急切） |
| `Heartbeat { ..., read_seq }` | 周期性捎带最新 read_seq；Follower 在 `HeartbeatResponse` 原样带回 |

丢失的 `Read` 可被后续心跳「补确认」，避免读永久卡住。

Follower 只有在**承认该发送方为领导**时才响应 Read / Heartbeat。

---

## 6. 读路径上各角色

| 角色 | 做 | 不做 |
|------|----|------|
| CLI / 任意节点 | 发 Read 请求 | 不本地扫盘当结果 |
| Follower | 转发；回 ReadResponse | 不 `state.read` 给客户端 |
| Candidate | Abort | — |
| Leader | 分配 seq、等多数、`state.read` | 不把读写入 Entry |

---

## 7. 与写的交错

```text
put 提交并 apply 之后
  → applied_index 前进
  → 之后的 get 在门闩与多数确认通过后
  → 一定能读到该 put（线性：写已完成再发起的读）
```

若 get 与 put 并发：结果可能是 put 前或后，但不会出现「已成功 put 却永久读不到」的线性违背（在领导稳定且消息最终送达前提下）。

---

## 8. 单节点

`cluster_size()==1`：广播 Read 后立刻 `maybe_read`；自己一票即多数。

---

## 9. 源码锚点

| 逻辑 | 位置 |
|------|------|
| 接收读请求 | Leader `Request::Read` |
| 门闩 + 出队 | `maybe_read` |
| Follower 确认 | `Message::Read` / Heartbeat 响应 |
| 状态机只读 | `Kv::read` / `State::read` |
