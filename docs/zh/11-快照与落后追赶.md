# 11. 快照与落后追赶

> **导航：** [← 10. 成员变更与领导转移](./10-成员变更与领导转移.md) · [12. 配置部署与进程运行时 →](./12-配置部署与进程运行时.md) · [索引](./README.md)

本文说明：**何时做本地快照并截断日志**、**落后节点如何靠 InstallSnapshot 追上**，以及快照字节存在哪。源码：`maybe_snapshot`、`maybe_send_append`、`InstallSnapshot` 处理、`Log::compact_to` / `reset_with_snapshot`。

---

## 1. 为什么需要快照

Raft 日志只增不减时：

- 磁盘无限涨  
- 新节点 / 长期离线节点必须重放**全部**历史 Entry  

快照 = 状态机在某 `applied_index` 的完整镜像 + 元数据，之后可 **删除该索引及以前的 Entry**。

本实现：

- **本地 compact**：Leader/Follower 在 apply 足够多后自己截断  
- **InstallSnapshot**：Leader 发现 peer 的 `next_index < first_index` 时整包发送（**不分块**）

---

## 2. 触发本地快照（`maybe_snapshot`）

在 `maybe_commit_and_apply` 成功 apply 后调用（领导转移 step_down 时跳过）。

条件（同时）：

```text
snapshot_threshold > 0
applied - snap_idx >= threshold     // 距上次快照至少 N 条
applied >= commit_index             // 已 apply 追上提交
能确定 applied 条目的 term（或等于 snap 基座）
```

动作：

```text
1. data = state.snapshot()
2. engine.set(Key::SnapshotData, data)      // 0x04
3. log.compact_to(applied, term)
     删除 Entry(first ..= applied)
     写 SnapshotMeta (applied, term)
     first_index = applied + 1
```

配置：`options.snapshot_threshold`（YAML，默认 1000；`0` = 关闭）。

---

## 3. compact 后日志形状

```text
之前: Entry(1)..Entry(1000)  commit=1000 applied=1000
之后:
  SnapshotMeta = (1000, term)
  SnapshotData = 状态机字节
  first_index  = 1001
  无 Entry(i) for i <= 1000
  之后新写从 1001 起
```

`Log::has` / `get` / `scan` 对 `< first_index` 的索引视为不在日志中（基座由 SnapshotMeta 描述）。

---

## 4. 落后节点：InstallSnapshot

### 4.1 何时发送

`maybe_send_append(peer)`：

```text
if progress.next_index < log.first_index():
  发送 InstallSnapshot {
    last_included_index,
    last_included_term,   // 来自 SnapshotMeta
    data: state.snapshot(),  // 当前状态机（应与快照点一致或更新）
    membership: active 配置,
  }
```

即：peer 要的下一条日志本地已经 compact 掉了，**只能发快照**。

### 4.2 Follower 处理

```text
1. 校验来自当前领导（否则忽略）
2. 若 last_included_index 过旧（< 本地 snap 或 applied）→ 不安装，仍 ACK
3. 否则:
     state.restore(data, last_included_index)
     engine.set(SnapshotData, data)
     log.reset_with_snapshot(index, term)   // 清空 Entry，设 commit/first/last
     membership.apply_entry(...)
4. InstallSnapshotResponse { last_included_index }
```

### 4.3 Leader 收到响应

```text
progress.advance(last_included_index)
maybe_send_append 继续发后续 Entry（快照点之后的日志）
```

---

## 5. 数据流图

```text
Leader apply 很多条
  → maybe_snapshot → BitCask: SnapshotData + 删旧 Entry

新节点 / 很旧的 Follower
  → next_index < first_index
  → InstallSnapshot 整包
  → Follower restore Kv + 重置日志
  → 再 Append 增量 Entry
```

---

## 6. 重启与快照

`raft-node` 启动：

```text
BitCask 打开
读 SnapshotData；若 SnapshotMeta.index > 0 → state.restore
Log::new 加载 first/commit/term
Node::new → maybe_apply 重放 first..commit 中尚未进状态机的尾部
```

详见 [13](./13-故障场景与测试对照.md) 重启一节。

---

## 7. 限制（教学实现）

| 点 | 现状 |
|----|------|
| 分块传输 | **无**，大状态一次发完 |
| 快照与 apply 并发 | 单线程 step，无并发 |
| 发送的 data | 当前 `state.snapshot()`，依赖本地已 apply 到至少快照点 |

---

## 8. 源码锚点

| 行为 | 位置 |
|------|------|
| 本地截断 | `maybe_snapshot` / `Log::compact_to` |
| 发送快照 | `maybe_send_append` 前半 |
| 安装 | Follower `InstallSnapshot` |
| 键 | `Key::SnapshotMeta` / `SnapshotData` |
