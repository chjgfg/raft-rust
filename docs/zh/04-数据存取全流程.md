# 04. 数据存取全流程

> **导航：** [← 03. 选举全流程](./03-选举全流程.md) · [05. 节点角色与职责 →](./05-节点角色与职责.md) · [索引](./README.md)

本文回答：**客户端 put/get 时，数据如何从「连上的从节点」到「主节点」，再如何进入 Raft 日志、BitCask，以及状态机 Kv。**  
源码主路径：`raft_cli` → `net` → `raft_node` → `node.rs` → `log.rs` → `session.rs` / `kv.rs` → `bitcask.rs`。

---

## 0. 先建立心智模型

有三层「数据」不要混：

| 层级 | 内容 | 位置 |
|------|------|------|
| **A. 客户端命令** | `put b banana` | CLI 内存 → TCP |
| **B. Raft 日志** | `Entry{index, term, command字节}` | **每个节点** BitCask 的 `Key::Entry(i)` |
| **C. 应用状态** | `b → banana` | **每个节点** 进程内 `Kv.data`（BTreeMap） |

客户端以为在「写数据库」；Raft 实际是：

1. 先把命令变成 **日志条目** 复制到多数节点；  
2. 再 **按序 apply** 进状态机；  
3. 读则在领导确认身份后读状态机。

**业务字符串键 `b` 不会作为 BitCask 的用户键直接存储**（本教学 KV）。BitCask 里主要是 Raft 元数据 + Entry。

---

## 1. 场景设定

```text
节点 1 Follower  :7001
节点 2 Leader    :7002
节点 3 Follower  :7003

用户执行：
  raft-cli --peers 127.0.0.1:7003 put b banana
  raft-cli --peers 127.0.0.1:7001 get b
```

即：**写打到从节点 3，读打到从节点 1。**

---

## 2. 写路径总览（从节点 → 主节点 → 存储）

```text
┌─────────┐  WireMsg::Client   ┌──────────────┐
│ raft-cli│ ─────────────────► │ node3:7003   │  Follower
└─────────┘                    │ raft-node    │
                               └──────┬───────┘
                                      │ ① 注入本地 ClientRequest
                                      │ ② 发现自己是 Follower
                                      │ ③ 转发 ClientRequest 给 Leader=2
                                      ▼
                               ┌──────────────┐
                               │ node2:7002   │  Leader
                               │              │
                               │ ④ propose    │──► Log.append ──► BitCask set Entry
                               │ ⑤ Append ────┼──► node1, node3
                               │ ⑥ 等多数 ACK │
                               │ ⑦ commit     │──► BitCask set CommitIndex
                               │ ⑧ apply      │──► SessionState → Kv.data["b"]="banana"
                               │ ⑨ ClientResp │──► 回到 node3 ──► 回到 CLI
                               └──────────────┘
                                      │
                                      │ Append + 后续 Heartbeat(commit_index)
                                      ▼
                               node1 / node3：splice 日志 + apply → 本地也有 b=banana
```

---

## 3. 写路径逐步拆解

### 步骤 ① CLI 编码

源码：`src/bin/raft_cli.rs`

1. 读/写 `.raft-cli-session`：得到 `client_id`，`seq = last_seq+1`  
2. `kv::encode(Command::Put { key: "b", value: "banana" })` → `cmd_bytes`  
3. 构造：

```text
Request::WriteSession {
  client_id: <uuid>,
  seq: N,
  command: cmd_bytes,   // 仅 Put 的 bincode，尚未加 SESS
}
```

4. TCP 连接到 **仅** `127.0.0.1:7003`（你只写了一个 peer）  
5. 发送帧：

```text
WireMsg::Client {
  id: <连接级 uuid，仅用于本 TCP 回复匹配>,
  request: WriteSession { ... },
}
```

**CLI 不关心谁是 Leader。**

---

### 步骤 ② node3 收包并注入 Raft

源码：`src/net/transport.rs` 连接线程 → `Inbound::Client`  
`src/bin/raft_node.rs` 主循环：

```text
收到 Client { request, reply_channel }
  req_id = Uuid::new_v4()          // Raft 内部 RequestID，≠ WireMsg.id
  client_replies[req_id] = reply_channel
  Envelope {
    from: 3,                       // 必须是本节点 id
    to:   3,
    term: node.term(),
    message: ClientRequest { id: req_id, request: WriteSession{...} },
  }
  node = node.step(envelope)
```

**此时数据还在 node3 进程内存里的 `Request`，未写 BitCask。**

---

### 步骤 ③ Follower 转发到 Leader（从 → 主）

源码：`Follower` 对 `ClientRequest` 的处理（`node.rs`）

```text
assert/检查 from == self.id
若 role.leader == Some(2):
  forwarded.insert(req_id)
  send(to=2, message=同一个 ClientRequest)   // 经 node_tx → PeerOutbox → TCP WireMsg::Raft
若无 leader:
  ClientResponse{ Abort } 给自己
```

网络上 node3 → node2：

```text
Envelope {
  from: 3, to: 2, term: T,
  message: ClientRequest {
    id: req_id,
    request: WriteSession { client_id, seq, command: put_bytes },
  }
}
```

| 节点 | 角色 | 这一步做什么 | 不做什么 |
|------|------|--------------|----------|
| 3 | Follower | 转发；记住 `forwarded` | **不** append 日志；**不**改 Kv |
| 2 | Leader | 下一步处理 | — |
| 1 | Follower | 无感知 | — |

**这就是「数据从从节点到主节点」：整包 ClientRequest 经 Raft 信封 TCP 发给 Leader。**

---

### 步骤 ④ Leader propose：命令进入 Raft 日志（→ BitCask）

源码：`Leader` 处理 `WriteSession` → `encode_session` → `propose`

#### 4.1 Session 包装

```text
log_command = b"SESS" ‖ bincode(SessionCommand {
  client_id,
  seq,
  payload: put_bytes,   // 仍是 kv::Command::Put 的 bincode
})
```

#### 4.2 Log::append

```text
Entry {
  index: last_index + 1,   // 例：42
  term:  当前领导 term,    // 例：6
  command: Some(log_command),
  membership: None,
}
engine.set(Key::Entry(42).encode(), bincode(Entry))
if fsync: engine.flush()
```

**BitCask 层：**

1. 逻辑键：`[0x00] + 42u64.to_be_bytes()`  
2. 逻辑值：bincode 后的 `Entry`  
3. 物理：在 `data/node2/bitcask.log` **文件末尾 append** 一条  
   `key_len | value_len | key | value`，并更新内存 keydir  

```text
┌─────────────────────────────────────────────┐
│  data/node2/bitcask.log（追加）               │
│  ...旧记录...                                 │
│  [新记录] key=Entry(42)  value=Entry结构体     │
└─────────────────────────────────────────────┘
        ▲
        │ Log::append
        │
   Leader 内存 last_index=42
```

#### 4.3 登记客户端等待

```text
writes[42] = Write { from: 3, id: req_id }
```

含义：这条日志提交并 apply 后，响应要回到 **from=3**（注入节点），再由其回 CLI。

#### 4.4 立即尝试复制

对每个 peer，若 `next_index == 42`，发 `Append`。

---

### 步骤 ⑤ 复制到 Follower（主 → 从）

#### 5.1 Leader 发出

```text
Envelope {
  from: 2, to: 1, term: 6,
  message: Append {
    base_index: 41,
    base_term:  <entry 41 的 term>,
    entries: [ Entry{index:42, term:6, command:Some(SESS|Put), ...} ],
  }
}
// 同样发给 to: 3
```

#### 5.2 Follower 处理 Append

```text
若 base 在本地日志匹配:
  log.splice(entries)     // 写入本地 BitCask Entry 键
  若含 membership 则立刻切换配置
  回复 AppendResponse { match_index: 42, reject_index: 0 }
否则:
  AppendResponse { match_index: 0, reject_index: ... }
```

| 节点 | BitCask | Kv.data |
|------|---------|---------|
| 2 Leader | 已有 Entry(42) | **尚未** apply（等提交） |
| 1 Follower | splice 后有 Entry(42) | 尚未 apply |
| 3 Follower | splice 后有 Entry(42) | 尚未 apply |

**注意：** 日志复制成功 ≠ 客户端已成功；还要 **多数 + 本任期提交 + apply**。

---

### 步骤 ⑥ 多数确认与提交

Leader 收到至少多数节点（含自己）的 `match_index >= 42`，且 `Entry(42).term == 当前 term`：

```text
log.commit(42)
  → engine.set(Key::CommitIndex, bincode((42, 6)))
  // commit 可以不 fsync
```

提交规则细节：只提交**本任期**产生的条目（旧任期条目靠 noop 间接提交）。

---

### 步骤 ⑦ apply：日志 → 状态机（仍在主节点）

```text
for entry in scan_apply(applied+1 ..= commit):
  SessionState::apply(entry)
    解码 SESS → 若 seq 已执行则返回缓存
    否则 Kv::apply
      data.insert("b", "banana")
      applied_index = 42
      返回 encode(Response::Put(42))
  查 writes[42] → ClientResponse {
    id: req_id,
    response: Ok(Response::Write(put_result_bytes))
  } 发给 from=3
```

**Leader 内存状态：**

```text
Kv.data = { ..., "b": "banana" }
```

**Leader BitCask：** 仍是 Entry/元数据；**没有**单独的 `b` 用户键。

---

### 步骤 ⑧ 响应回到 CLI

```text
node2 出站 Envelope to=3 ClientResponse
  → TCP → node3
node3 Follower:
  若 id 在 forwarded 中 → 再发给 to=self ClientResponse
node3 主循环:
  client_replies[req_id].send(Ok(Response::Write(...)))
  → 连接线程 WireMsg::ClientReply
  → CLI 打印 Put 的索引或 Display
```

---

### 步骤 ⑨ Follower 侧状态机何时有数据？

两条路径：

1. **Heartbeat** 携带更大的 `commit_index`，且 follower 日志已匹配 `last_index`  
   → `log.commit` + `maybe_apply` → 本地 `Kv` 也 insert  
2. 之后任何会 `maybe_apply` 的路径  

因此：  
- **日志**在 Append 时就到了从节点；  
- **Kv 业务状态**在 commit 通知后才到从节点。  

客户端 `get` 不读从节点本地 Kv，而是再走领导读（见下节）。

---

## 4. 读路径总览（从节点 → 主节点 → 读状态机）

```text
CLI get b → TCP → node1 (Follower)
  → ClientRequest{ Read(bincode(Get{b})) }
  → 转发 Leader node2
  → Leader:
       read_seq += 1
       reads 队列放入该读
       广播 Message::Read { seq }   // 或靠 Heartbeat 带 read_seq
  → Follower 回 ReadResponse / HeartbeatResponse
  → 多数确认 read_seq 后:
       要求 commit_term==当前term 且 applied 追上
       Kv::read(Get{b}) → Some("banana")
  → ClientResponse 回 node1 → CLI
```

| 对比 | 写 | 读 |
|------|----|----|
| 是否写 Raft 日志 | 是 | **否** |
| 是否改 BitCask Entry | 是 | 否 |
| 是否改 Kv | apply 时 | **否**（只读） |
| 多数用途 | 提交日志 | 确认「我还是领导」 |

---

## 5. Scan 与 Status

| 命令 | 路径 |
|------|------|
| `scan` | 同读：`Request::Read(Scan)` → Leader `Kv::read` → 整表 `BTreeMap` 编码返回 |
| `status` | `Request::Status` → 仅 Leader 填 `Status{leader,term,match_index,commit,applied,voters,storage}` |

Follower 收到同样**转发**到 Leader。

---

## 6. 单节点简化路径

`peers: []` 时：

```text
CLI → node1(Leader)
  propose → append Entry → 法定人数=1 → 立刻 commit+apply
  → 响应 CLI
```

无转发、无 Append 网络。

---

## 7. 端到端数据变化表（写 `b=banana`）

| 时刻 | node3 日志 | node2 日志 | node1 日志 | 各节点 Kv |
|------|------------|------------|------------|-----------|
| CLI 刚连上 3 | 旧 | 旧 | 旧 | 无 b |
| 3 转发后 | 旧 | 旧 | 旧 | 无 b |
| 2 append 后 | 旧 | **+Entry42** | 旧 | 无 b |
| 1、3 append ACK 后 | **+Entry42** | Entry42 | **+Entry42** | 无 b |
| 2 commit+apply 后 | Entry42 | Entry42+commit | Entry42 | **2 有 b** |
| Heartbeat 推进后 | commit+apply | 同左 | commit+apply | **全都有 b** |
| CLI 收到成功 | — | — | — | 用户可见成功 |

---

## 8. 失败与 Abort

| 情况 | 结果 |
|------|------|
| 无 Leader / 选举中 | `Error::Abort`，CLI 换 peer 重试 |
| 转发后领导切换 | `abort_forwarded`，Abort |
| 写已 apply 但响应丢失 | 同一 `WriteSession(client_id,seq)` 重试 → Session 返回缓存，不双写 |
| 只连一个挂掉的 peer | CLI 超时失败（建议 `--peers` 写多个地址） |

---

## 9. 源码锚点

| 步骤 | 位置 |
|------|------|
| CLI put | `src/bin/raft_cli.rs` |
| TCP Client | `src/net/transport.rs` `run_client_request` / `handle_conn` |
| 注入 | `src/bin/raft_node.rs` |
| 转发 | `Follower` `ClientRequest` 分支 |
| 写日志 | `Leader` `propose` / `Log::append` |
| 复制 | `maybe_send_append` / Follower `Append` |
| 提交应用 | `maybe_commit_and_apply` |
| Session/Kv | `session.rs` / `kv.rs` |
| 读 | `Leader` `Read` + `maybe_read` |
